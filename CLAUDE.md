## Git commit protocol
 
Use English for every commit message. Preserve Danish domain terms and UI
labels when translating them would make the message less precise.
 
### Commit boundaries
 
- Each commit must represent one coherent behavior or technical change.
- Split unrelated UI, API, database, and calculation changes into separate
  commits.
- Include tests and migrations in the commit that requires them.
- Fold corrections made during the same task into the original change rather
  than creating "fix previous commit" commits.
- A commit should leave the repository in a working state.
- Do not commit unfinished experiments, debugging output, commented-out code,
  or temporary files.
 
Before staging changes:
 
1. Run `git status`.
2. Inspect the relevant unstaged diff.
3. Inspect recent commit messages with `git log -10 --oneline`.
4. Group changes by observable behavior.
5. If the working tree contains unrelated changes, propose a commit plan before
   staging anything.
 
Only stage files or hunks created or changed for the current task. Never use
`git add .` or `git add -A` when unrelated work may exist. Never discard,
overwrite, or include another person's changes.
 
### Message format
 
Use:
 
    type(scope): imperative summary
 
Allowed types:
 
- `feat`: new user-visible behavior
- `fix`: defect correction
- `perf`: performance improvement
- `refactor`: internal restructuring without behavior changes
- `test`: test-only change
- `docs`: documentation-only change
- `build`: dependencies or build configuration
- `chore`: repository maintenance that fits no other type
 
Use a short, stable domain as the scope. Prefer these scopes:
 
- `engine`
- `optimization`
- `rotations`
- `fertilizer`
- `emissions`
- `database`
- `api`
- `ui`
 
Message rules:
 
- Start the summary with a lowercase imperative verb such as `add`, `fix`,
  `remove`, `preserve`, `avoid`, or `calculate`.
- Keep the complete subject at 72 characters or fewer when practical.
- Do not end the subject with a period.
- Describe the resulting behavior, not the files edited.
- Avoid vague subjects such as "updates", "changes", "fix stuff", "cleanup",
  "Claude changes", or "work in progress".
- Choose the primary domain when a change crosses several layers. Do not put
  several scopes in one subject.
- Add a body when the reason, constraint, or calculation rule is not obvious.
  Explain why the change is necessary and name important domain invariants.
- Do not repeat the subject in the body.
- Never claim that checks passed unless they were run successfully.
- Do not add AI attribution, "generated by Claude", or an AI
  `Co-authored-by` trailer.
 
Generate the message from the staged diff, not from the conversation or task
description.
